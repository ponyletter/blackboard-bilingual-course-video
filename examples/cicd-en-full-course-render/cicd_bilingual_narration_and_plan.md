# CI/CD 双语教学视频脚本：为什么大公司依赖它，小公司却常常手动发版？

> 课程结论：CI/CD 不是“把部署命令写进脚本”这么简单，也不是任何团队都必须立刻全自动上线。它是一组将构建、测试、制品、部署、审批、观察和回滚做成**可重复、可验证、可追溯**流程的工程实践。大公司依赖它，往往因为多人、多服务、多环境和合规要求放大了人工发布的不确定性；小团队则可以从可版本化脚本与基本测试开始，逐步演进。[1] [2] [3] [4]

## 场景脚本

| 场景 | 中文旁白与字幕 | English narration and captions | 黑板画面卡片 | 小总结 |
|---|---|---|---|---|
| 1 | 为什么大公司几乎离不开 CI/CD，而不少小团队仍靠人工发版，甚至只保留一段部署脚本？这不是谁更专业的站队题。真正的问题是：代码从提交到用户看到的过程中，哪些风险必须被系统拦住，哪些环节可以暂时由人判断。团队规模、变更频率、系统复杂度和失败代价，会给出不同答案。 | Why do large organizations often rely on CI/CD, while many small teams still release manually or keep only a deployment script? This is not a question of who is more professional. The real question is which risks must be stopped by a system between a commit and a customer-facing release, and which decisions can still be made by people. Team size, change frequency, system complexity, and failure cost lead to different answers. | 发布风险；团队规模；变更频率；系统复杂度；失败代价；人工判断 | **先换问题：**CI/CD 不是信仰，而是管理交付风险的方式。 |
| 2 | CI 是持续集成：开发者频繁把代码合入共享仓库，每次变更自动触发构建、测试和集成检查。它的核心不是“自动跑一下命令”，而是尽早发现回归，让每个人都基于可工作的版本继续开发。没有快速反馈，后面的部署自动化只会更快地放大问题。 | CI means continuous integration: developers frequently merge changes into a shared repository, and each change automatically triggers builds, tests, and integration checks. Its core is not merely running a command automatically. It is finding regressions early, so everyone can keep building on a working version. Without fast feedback, later deployment automation only amplifies problems faster. | 共享仓库；自动构建；自动测试；集成检查；快速反馈；回归发现 | **CI 的第一价值：**尽早知道这次改动是否仍然可用。 |
| 3 | CD 有两种常见含义。持续交付把通过验证的变更自动送到生产就绪环境，最后是否上线仍可由人批准；持续部署则在满足所有门禁后直接面向用户发布。两者都不是“自动上线”的同义词。对风险较高、合规较强或测试尚未成熟的业务，保留人工审批往往是合理控制，而不是落后。 | CD commonly has two meanings. Continuous delivery automatically brings verified changes to a production-ready environment, while a person may still approve the final release. Continuous deployment sends changes to customers after all required gates pass. Neither term simply means “deploy automatically.” For high-risk, regulated, or insufficiently tested systems, human approval can be a sensible control rather than a sign of immaturity. | 持续交付；生产就绪；人工批准；持续部署；自动门禁；风险控制 | **CD 的关键区别：**自动到哪里，以及谁拥有最终发布权。 |
| 4 | 所以，“我有一段发布脚本”不等于我已经有 CI/CD。脚本当然很重要，它可以是流水线中的一个作业；但完整交付还需要定义触发条件、隔离运行环境、测试门禁、制品版本、密钥管理、部署记录、回滚路径和失败告警。缺其中几项不代表不能发布，却意味着风险仍靠个人记忆和临场操作承担。 | So, “I have a deployment script” does not mean “I have CI/CD.” A script matters and can be a job inside a pipeline. But reliable delivery also defines triggers, isolated runners, test gates, artifact versions, secret handling, deployment records, rollback paths, and failure alerts. Missing some of these does not make releases impossible; it means risk is still carried by personal memory and live operations. | 触发条件；运行环境；测试门禁；制品版本；密钥管理；回滚告警 | **脚本是原料，**CI/CD 是把交付变成受控系统。 |
| 5 | 大公司普遍依赖 CI/CD，通常不是因为它们喜欢更复杂的工具，而是人工操作在多人、多服务、多环境下会迅速失控。谁发布了哪个版本？同一制品是否经过相同测试？敏感配置谁能读取？失败能否立刻停止或回滚？这些问题需要可重复流程、权限边界和审计记录来回答。流水线把经验变成团队共同遵守的机制。 | Large organizations usually rely on CI/CD not because they enjoy more complicated tools, but because manual work becomes hard to control across many people, services, and environments. Who released which version? Did the same artifact pass the same tests? Who can read sensitive configuration? Can a failure stop or roll back quickly? These questions require repeatable workflows, permission boundaries, and audit records. Pipelines turn experience into mechanisms the whole team can follow. | 多人协作；多服务；多环境；权限边界；审计记录；快速回滚 | **规模放大的不是代码量，**而是交付过程中的不确定性。 |
| 6 | 小团队选择手动发版，也不必然错误。变更少、服务简单、负责人明确、上线窗口可控时，人工检查可能比搭建复杂平台更划算。但风险在于把流程锁在某个人的电脑和记忆里。更稳妥的起点，是把脚本提交进仓库，固定输入和输出，记录版本和结果，再逐步加入构建、测试、制品与部署审批。 | Manual release is not automatically wrong for a small team. When changes are rare, services are simple, ownership is clear, and release windows are controlled, human checks may cost less than building a complex platform. The risk comes when the process is locked inside one person’s laptop and memory. A safer starting point is to commit scripts to the repository, make inputs and outputs repeatable, record versions and results, then gradually add builds, tests, artifacts, and deployment approval. | 变更较少；服务简单；责任明确；脚本入库；记录版本；逐步演进 | **小团队的目标不是复制大厂，**而是减少对个人记忆的依赖。 |
| 7 | 成熟度可以一层层增加：先让构建和单元测试自动运行；再生成不可变制品并保存版本；然后把部署写成可重复声明；随后增加环境审批、灰度或金丝雀、监控和回滚。每增加一层，都是在回答一个具体风险，而不是为了把 YAML 写得更长。CI/CD 的价值在于让交付能力随系统复杂度一起成长。 | Delivery maturity can grow layer by layer: first automate builds and unit tests; then create immutable artifacts and retain versions; next make deployments repeatable and declarative; then add environment approvals, gradual rollout or canaries, monitoring, and rollback. Each layer answers a specific risk. It is not about writing longer YAML. CI/CD matters because delivery capability can grow with system complexity. | 自动构建；自动测试；不可变制品；声明式部署；灰度发布；监控回滚 | **正确演进路径：**每一步自动化，都要对应一个真实风险。 |
| 8 | 主流工具不是互斥的“框架阵营”，而是不同位置的工具链。GitHub Actions 和 GitLab CI/CD 适合把代码托管与流水线结合；Jenkins 适合可自建、可扩展的 Pipeline as Code；CircleCI 等提供云托管流水线；Argo CD 和 Flux 偏向 Kubernetes 的 GitOps 持续交付；Tekton 则提供可组合的云原生流水线构件。它们经常一起出现。 | Mainstream tools are not rival “framework camps.” They occupy different places in a toolchain. GitHub Actions and GitLab CI/CD combine code hosting and workflows; Jenkins supports self-managed, extensible Pipeline as Code; services such as CircleCI provide hosted pipelines; Argo CD and Flux focus on GitOps continuous delivery for Kubernetes; and Tekton provides composable cloud-native pipeline building blocks. They often appear together. | GitHub Actions；GitLab CI/CD；Jenkins；托管流水线；Argo CD / Flux；Tekton | **选工具先看职责，**再看生态、托管方式和现有基础设施。 |
| 9 | 最后，用四个问题判断下一步：我们最常发生的发布失败是什么？哪些检查可以自动化且足够快？哪一步必须由人批准？失败后如何定位、停止和回滚？如果答案还模糊，就先不要追求全自动部署。先把一次发布做成可重复、可观察、可审计的流程，再让自动化逐步替代不必要的人工动作。 | Finally, use four questions to decide the next step: What release failure happens most often? Which checks can be automated and remain fast enough? Which step still needs human approval? How will we locate, stop, and roll back a failure? If those answers are unclear, do not chase fully automated deployment yet. First make one release repeatable, observable, and auditable; then let automation gradually replace unnecessary manual work. | 常见失败；自动检查；人工批准；故障定位；停止回滚；持续改进 | **最好的 CI/CD，**不是最复杂的流水线，而是最适合当前风险的交付系统。 |
