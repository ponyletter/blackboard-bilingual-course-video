# 为什么大公司离不开 CI/CD
# 小团队手动发版就错了吗

CI/CD 常被讲成“自动部署”，也有人把一段发布脚本叫 CI/CD。其实它是把构建、测试、制品、部署、审批和回滚做成可重复流程的工程实践。大公司依赖它，是为了把多人协作的发布风险交给系统控制。

小团队手动发版也不等于不专业。若变更少、服务简单、责任明确，人工检查可能更划算；关键不在是否全自动，而在发布是否可重复、可观察、可追溯，以及失败时能否安全停下和恢复。

## 一、先分清 CI、持续交付与持续部署

CI 的核心是频繁把代码合入共享仓库，并在每次变更后自动构建、测试和集成检查，让问题尽早暴露。持续交付会把通过验证的版本自动送到生产就绪环境，但最终上线可以由人批准；持续部署则在所有门禁通过后直接发布给用户。三者共同目标是更快、更可靠地交付，而不是单纯追求上线更快。

## 二、部署脚本很重要，但它只是交付系统的一块

一段脚本可以执行部署，也可以成为流水线的一个作业；但成熟交付还要定义触发条件、隔离的运行环境、测试门禁、制品版本、密钥管理、部署记录、失败告警和回滚路径。缺少这些环节并不意味着不能发版，却意味着风险可能仍锁在某个人的电脑、口头知识和临场操作里。

## 三、大公司依赖 CI/CD，是因为规模会放大人工不确定性

当多人同时修改多个服务，并要部署到测试、预发和生产等环境时，人工操作最难保证一致性。谁发布了哪个版本、是否使用同一制品、敏感变量谁能读取、失败能否停止和回滚，都需要可重复流程、权限边界与审计记录。流水线的价值是把个人经验沉淀成团队共同遵守的交付机制。

## 四、工具不必站队，应按交付职责组合

GitHub Actions、GitLab CI/CD 适合代码托管与工作流结合；Jenkins 适合自建和扩展；CircleCI 提供托管流水线；Argo CD、Flux 偏向 Kubernetes GitOps 持续交付；Tekton 提供云原生流水线构件。选型应看现有平台、运行环境、合规要求和团队能力，不必把工具当成互斥阵营。

最好的 CI/CD 不是最长的 YAML，也不是盲目全自动上线。先找最常见的发布风险，把一次发布做成可重复、可观察、可回滚的流程，再逐步自动化。
